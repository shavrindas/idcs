
컨트롤러 특성: 
성능과 일관성을 위해 추가되는 컨트롤러는 비동기(SQLAlchemy 2.0 스타일) 문법을 기준으로 작성





1. Session vs AsyncSession 선택 기준과 올바른 방향성
결론부터 말씀드리면, 비동기(AsyncSession) 방식을 기본 패러다임으로 채택하고, 
쓰기 작업(인입)과 읽기 작업(조회)을 최적화하는 방향이 정답입니다.

왜 AsyncSession이어야 하는가?
I/O Bound 병목 제거: 수많은 IoT 디바이스가 밀어내는 
실시간 수치 데이터 저장과 사용자들의 대시보드 조회는 전형적인 I/O Bound 작업입니다. 
동기(Session) 방식은 데이터베이스 응답을 기다리는 동안 
FastAPI의 워커 스레드를 블로킹(Blocking)하므로 동시 접속자가 늘어날 때 즉각 반응성 저하와 타임아웃을 유발합니다.

커넥션 풀 효율성: 비동기를 사용하면 훨씬 적은 수의 DB 커넥션으로도 
대규모의 동시 요청(Concurrently)을 가볍게 처리할 수 있습니다.

① 실시간 쓰기 경로: Redis 버퍼(Buffer) 도입 권장
FastAPI가 직접 DB(TimescaleDB)에 실시간으로 개별 INSERT를 날리는 방식은 커넥션 고갈과 디스크 I/O 병목을 유발합니다.
흐름: IoT 기기 ──> FastAPI ──> Redis (In-Memory Buffer) ──> (배치 벌크 인서트) ──> TimescaleDB
2~3초 혹은 일정 크기(예: 500개)로 데이터를 Redis에 임시 수집한 뒤, 백그라운드 태스크나 별도 프로세스를 통해 bulk_insert하는 방식을 취하면 DB 부하를 1/10 이하로 낮출 수 있습니다.

② "현재 데이터가 제일 중요" -> Redis 캐싱으로 모니터링 성능 극대화
모니터링 화면에서 호출하는 "최신 데이터" API를 매번 TimescaleDB에서 ORDER BY timestamp DESC LIMIT 1로 조회하는 것은 비효율적입니다.
데이터가 들어오는 즉시 Redis에 해당 디바이스의 최신 상태(Latest State)를 SET 해둡니다.
모니터링 API는 TimescaleDB에 접근하지 않고 오직 Redis 캐시만 즉시 조회하여 응답속도를 1ms 미만으로 유지합니다.
